# Office security audit playbook

The audit is read-only. A finding needs evidence; a clean scanner run is not a verdict.

```
- [ ] 1 Scope   - [ ] 2 Inventory   - [ ] 3 Threat model   - [ ] 4 Verify by area
- [ ] 5 Local scans   - [ ] 6 Evidence and severity   - [ ] 7 Route and retest
```

## Modes (the brief names one)

| Mode | When | You do |
| --- | --- | --- |
| `pre-code` | T2/T3, in parallel with the developer | **Finish before the developer does: at most ~8 tool calls, no reference files, no audit, no running tests.** From the brief's contract only: a threat model of at most 10 lines at the top of `.empresa/handoff/<task>-security.md`, and one black-box test file `tests/security/<task>.test.ts` with one test per abuse case (other user's resource, missing or forged token, hostile input, limits, rate limit, enumeration). The tests fail until the code exists; that is expected. Return the two paths. |
| `verify` | T2 with external input or T3, after the developer (T3: after the Claude Security scan): you are the only verifier | steps 4-7 on the diff range (and `triage` of the scan report when you get one), **plus** the code review from the `office-review` checklist: diff, then tests, then code; correctness (errors, limits, nulls, concurrency), a test for every new behavior and error, nothing out of scope, contract kept. Run the test command yourself. Verdict, and when approved a commit summary (type, English message, why and how verified, files). |
| `checkpoint` | T3, after each slice | steps 4-7 on that slice's diff only; critical/high stops the next slice |
| `triage` | after Claude Security | read `CLAUDE-SECURITY-RESULTS.md`, confirm reachability, drop false positives with a reason, route the rest |
| `full` | first audit of an existing project | all steps, starting with `reference/ai-generated-code.md` |

When you are continued with `SendMessage`, you keep your earlier context: reuse the threat model, read only the new diff.

## 1. Scope
The diff plus its blast radius (`graphify query` on the changed symbols). End-of-project audit: every entry point. Read the security level set by the architect (`L1` default, `L2` for personal data, payments, multi-tenant, admin). No level set: assume `L2` if any of those are present. Write down what is **out** of scope.

## 2. Inventory
- **Assets**: credentials and tokens, personal data, money, admin actions, other tenants' data, the AI model's tools and context.
- **Entry points**: routes, forms, file uploads, webhooks, query strings, headers, background jobs, LLM prompts and retrieved documents.
- **Trust boundaries**: browser ↔ server, server ↔ database, server ↔ third parties, tenant ↔ tenant, user ↔ admin.

## 3. Threat model
For each boundary the change touches, ask the STRIDE questions and write one abuse case per relevant letter: **S**poofing (act as someone else), **T**ampering (change data or requests), **R**epudiation (deny an action, no log), **I**nformation disclosure, **D**enial of service, **E**levation of privilege. Skip letters that do not apply; do not pad.

## 4. Verify by area
Read **only** the references for areas the scope touches. Each lists what to check and how to prove it.

| The change touches | Read |
| --- | --- |
| login, sign-up, password reset, sessions, tokens, MFA | [reference/auth-session.md](reference/auth-session.md) |
| who can read or change which record; roles; tenants; Supabase RLS | [reference/access-control.md](reference/access-control.md) |
| any external input, queries, HTML output, uploads, server-side fetch | [reference/input-injection.md](reference/input-injection.md) |
| secrets, env, headers, CORS, cookies, error messages | [reference/secrets-config.md](reference/secrets-config.md) |
| new or updated dependency, build, CI | [reference/supply-chain.md](reference/supply-chain.md) |
| an LLM feature, agent, tool use, RAG | [reference/llm.md](reference/llm.md) |
| personal data collected, stored, logged or shared | [reference/lgpd.md](reference/lgpd.md) |
| code largely generated by AI, or a first audit of a project | [reference/ai-generated-code.md](reference/ai-generated-code.md) |

`L1`: check every item marked in the reference. `L2`: also the items marked `L2`.

## 5. Local scans (never install, never auto-fix)
Detect the package manager first. Run what is installed and mask secrets in output:
`npm audit --audit-level=high` · `pnpm audit` · `composer audit` · `pip-audit` · `gitleaks git --redact` (or `gitleaks detect --redact` on older versions).
Never `audit fix`, `update`, or unreviewed scripts. Tool missing: record "not run: <tool> not installed" and continue manually.
Scanner output is a lead, not a finding: confirm reachability before reporting.

## 6. Evidence and severity
A finding is: vulnerable code at `path:line` + an input the attacker controls + a non-destructive proof (a failing test, a request and response against the local app, or a traced data flow). Without proof it goes under "to verify". Never test against production; never exfiltrate real data.

| Severity | Meaning | Delivery |
| --- | --- | --- |
| Critical | unauthenticated access to data or actions, remote code execution, exposed live secret | blocks |
| High | authenticated user reaches others' data or admin actions; injection; auth bypass needing some condition | blocks |
| Medium | needs unusual conditions or has limited impact (missing rate limit, verbose errors, weak headers) | fix recommended, deadline |
| Low | hardening, defense in depth | note |

Rate by what an attacker gains and how easily, not by the category name.

## 7. Route and retest
Finding template, one block each, in `.empresa/handoff/<task>-security.md`:

```
[SEVERITY] <title>
Where: <path:line>   Area: <auth | access | input | secret | config | dependency | llm | privacy>
Asset / boundary: <what is exposed, across which boundary>
Proof: <steps or test; request and masked response>
Impact: <what the attacker gains>
Fix: <the control that closes it>   Owner: <role>
Verify after fix: <the test or request that must now fail safely>
```

End the file with: areas audited, scans run and their result, what was not covered and why, and the verdict. After the owner's fix, rerun the proof and the related regression: **confirmed** or **reopened**, with new evidence.

For an area no reference covers, load `security-and-hardening` once.
